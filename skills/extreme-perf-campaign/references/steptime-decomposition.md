# 步长归因：先分固定成本与边际成本，再谈优化（P0 之后、P1 之前）

> 2026-10-20 在 DeepSeek-V4.1-Flash / 8×910B3 上补的一课。
> 已经被 `extreme-perf-campaign` 的 P0/P2 部分吸收，这里给可复制的做法。

## 为什么要先做这一步

一个 decode 步的时间由两部分组成：

```
step(n) = F + n · c
          ↑     ↑
          固定   边际
```

- **F（固定成本）**：与并发请求数无关的部分。通常是**权重流式读取**——
  一个 MoE 层只要被调用，就要把它的专家权重从 HBM 搬进计算单元，
  搬多少与这一批有多少 token 基本无关（见下方 §3 的 AllGather 分析）。
- **c（边际成本）**：每多一个并发请求增加的部分——多出的 token 要走 attention、
  MoE 路由和集合通信。

**F 和 c 的优化手段完全不同**：F 靠提高带宽利用率或减少搬运字节；c 靠压缩算子、
减少同步。**不知道自己在优化哪一项，就一定会优化错对象。**

## 1. 三步测出 F 和 c（都不需要重启引擎）

```bash
# 三步：并发 1 / 2 / 4，同一 prompt，同一输出长度
for n in 1 2 4; do
  python3 concurrency_probe.py http://127.0.0.1:<PORT> longgen-prompt.json <n> 256
done
```

输出形如（DeepSeek-V4.1-Flash / A2 实测）：

| n | ms/step | A | 每 token |
|---:|---:|---:|---:|
| 1 | 35.52 | 5.82 | 5,208 µs |
| 2 | 42.24 | 5.82 | 3,097 µs |
| 4 | 48.10 | 5.82 | 1,763 µs |

解 `step = F + n·c`：

```
c = (48.10 − 35.52) / (4 − 1) = 4.19 ms/请求
F = 35.52 − 4.19            = 31.33 ms   ← 占单请求步长的 88%
```

**判读**：
- F 占 80% 以上 ⇒ 这是**权重流式受限**的部署，单流优化只能动 F。
- F 很小、c 很大 ⇒ 算力受限，优化要压算子/减少重复计算。
- 两者都不大但吞吐上不去 ⇒ 很可能有**同步点或调度空洞**，去查串行段与内核数。

## 2. 用带宽账给 F 定价（判断还有多少空间）

```bash
# a) 每步每 rank 必读的专家权重字节（结构式）
#    3 个矩阵 × moe_intermediate × hidden × 0.5 B(int4) × (n_routed/EP) × n_layers
python3 - <<'PY'
per_expert = 3*2304*5120*0.5            # W4A8: 17.7 MB
per_rank   = per_expert*48*40/1e9       # 48 local experts × 40 layers
print(f"{per_rank:.1f} GB/step")
PY

# b) 交叉验证：从权重仓抽样求专家权重占比
#    safetensors 遍历键名，按 dtype 折算字节，取 "experts" 键占比 × 主干总字节 / EP

# c) 实测 HBM 读带宽（本机，别用规格书数字）
python3 hbm_bw.py     # torch.sum / copy_，0.05–0.2 GiB，200 次平均

# d) AICore 稳态占用（有负载时读）
npu-smi info | grep -E "^\| [0-9]+ +910"
```

**A2 实测**（1017 权重）：F = 31.3 ms、35.8 GB/步 ⇒ **1143 GB/s**；
本机 HBM 实测峰值 **1763 GB/s** ⇒ **利用率 65%**。

**读法**：
- 利用率 < 70% 且 AICore > 90% ⇒ 搬运与计算没有充分重叠，**这是还有量级的地方**。
- 利用率 > 90% ⇒ 除非减少字节，否则已到物理上限，**继续调实现是浪费**。

## 3. 减少字节之前，先确认"必读全部专家"是不是通信形态的数学后果

这一步能省掉一整轮白费力气的实验。

**AllGather MoE**（每个 rank 拿到**全部** token，只用自己的专家算）：

```
每步 token 总数 = EP × 每 rank token 数
每步路由决策   = token 总数 × topk
摊到本 rank 的 local_experts = (EP × tokens × topk) / local_experts 个 token/专家
```

DeepSeek-V4.1-Flash / A2 / EP8 / batch=1 / A=5.82：
`48 token × top-6 = 288 决策 ÷ 48 专家 = 6.0 token/专家` ⇒ **48 个专家全部命中**。

⇒ **AllGather 下"每步必读全部本地专家"是数学必然，不是实现低效。**
这时去优化 GMM 的稀疏读没有意义——它已经把该读的都读了。

**All2All dispatch**（每个 rank 只收发给自己的 token）：每 rank 命中降到 `288/8 = 36` 次，
distinct 专家数远小于 48 ⇒ 读取量降一个量级。**但代价是每步多两次集合通信**，
单流短步长下未必划算——**必须实测，不能只凭算术拍板**。

## 4. 结论模板（写进证据文件时用）

```
实测步长        F + c = 31.3 + 4.19n
固定成本占比    88%
必读字节        35.8 GB/rank/step（两种独立算法互校：结构式 34.0 / 分片式 35.8）
有效带宽        1143 GB/s
实测带宽峰值    1763 GB/s  ⇒ 利用率 65%
AICore 占用     89–99%
判定           权重流式受限；若利用率提到 90% ⇒ 1.30–1.57×
下一步          ① 提高搬运/计算重叠（唯一还有量级的单流杠杆）
                ② 换 All2All 减少必读字节（须实测通信代价）
                ③ 小算子融合（8–10% 打折后，优先级最低）
```

## 5. 反面教材（本次踩到的）

- **拿"设备占空比 94%"直接推断"算力受限"**——要同时看带宽利用率。
  算力满而带宽空，恰恰说明是在等权重，不是算得慢。
- **拿"AI core 空闲 X ms"直接当成可回收**——空闲是 21 个/步、中位 69 µs 的
  弥散气泡，不是一个大洞；能回收多少取决于能不能把它们连起来（融合/预取），
  不是把空闲时间加起来。
- **用重复拼接文本伪造"长上下文"做扫描**——模型会立刻 EOS，
  得到的是 A 掉到 2.4 的假数据。要测上下文长度影响，必须用**真实语义连续的前缀**。
