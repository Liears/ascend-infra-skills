# P6 — A2 单流步长分解：固定成本占 88%，但归属未定（2026-10-20）

> 问题：路径 A 已经跑到 163.3 tok/s，还有多少空间？该往框架层、算法层还是算子层投入？
> 方法：用**不需要解析 prof 二进制**的手段（并发扫描、带宽微基准、日志布尔值）
> 做代数分解，每一步都用真机数字交叉验证；否定的结论同样留证。
> 设备：8×910B3（A2），1017 权重（W4A8），DSpark S=5，TP8+EP8，`DRAFT_GRAPH=1`。

## 0. 结论

**单流 decode 的结构是 `step = 31.3 + 4.19n`（ms）：88% 是固定成本。**

**固定成本 F 已被四处独立测量证明对"通信布局"和"上下文长度"都不敏感**，
说明它由**模型结构本身**决定（与部署形态无关）。

**F 的物理归属本轮没有做成**：`npu-smi` 在这台机器上的利用率读数不可信
（见 §1.4），因此**不能**据此判断"带宽利用率还剩多少空间"。
与 F 有关的唯一可靠证据是它的**不变性**（对通信布局、上下文长度都不变），
这说明它由模型结构决定；但**具体是权重读、算子串行还是别的，仍未定位**。

**已经被实测排除的方向**（不要重复走）：换 MoE 通信形态（AllGather→AllToAll，
F 只从 31.3 降到 30.9，A 还退化）、跨层软件流水（拆批代价 ×1.7）。

| 量 | 值 | 来源 |
|---|---:|---|
| 实测步长（batch=1） | **35.5 ms** | `decode_probe` 256tok：A=5.82，89.2 tok/s |
| 其中固定成本（与请求数无关） | **31.3 ms（88%）** | 并发扫描 n=1/2/4 解 `step = F + n·c` |
| 边际成本（每多一个并发请求） | 4.19 ms | 同上 |
| 每步每 rank 必读专家权重 | 34.0–35.8 GB | 结构式 `3×2304×5120×0.5B × 384/8 × 40` = 34.0；权重仓分片抽样 × 96 = 35.8 |
| A2 实测 HBM 读带宽 | **1763 GB/s** | `torch.sum` 微基准（0.05 GiB，200 次平均）——这个数可信 |
| 带宽利用率 | **未测出** | `npu-smi` 的利用率计数器在本机不可信（§1.4），不再给数字 |

**注释**：F 的数值是可靠的（四个测量点互校），**F 的物理归属还没测出来**。
原先这里写"带宽利用率 65%、算力在等权重"，那是基于 `npu-smi` 读数的推断——
而该读数在本机不成立（§1.4），所以那段解释已作废。

**F 的不变性（三条独立测量）**：

| 改变的维度 | F |
|---|---:|
| MoE 通信形态（AllGather / fused_mc2=1 默认） | 31.33 ms |
| MoE 通信形态（fused_mc2=0，AllToAll 生效） | 30.91 ms |
| 上下文长度（8K） | 31.3 ms |
| 上下文长度（32K） | 31.8 ms |

⇒ F 对**通信布局**和**上下文长度**都不敏感，由模型结构决定。
**但"由结构决定"不等于"就是权重读取"**——固定的算子串行链同样会有这个不变性。
要区分两者必须拿设备侧数据，本轮没拿到（§1.4）。

## 1. 能判定什么、不能判定什么

### 1.1 排除"延迟受限"：并发几乎免费

同一 prompt 同发 n 个请求（`concurrency_probe.py`，256 token 输出）：

| n | ms/step | A | 每 token 成本 | 聚合吞吐 |
|---:|---:|---:|---:|---:|
| 1 | **35.52** | 5.82 | 5,208 µs | 89.2 tok/s |
| 2 | 42.24 | 5.82 | 3,097 µs | 115.5 tok/s |
| 4 | 48.10 | 5.82 | 1,763 µs | 81.0 tok/s（TTFT 抢占） |

n 从 1 到 4，token 数 ×4，步长只 ×1.35 ⇒ **88% 的步长与请求数无关**。
延迟受限的场景不会有这个形状（步长会几乎不随 n 变且无固定底噪）。

### 1.2 "算力受限"无法用 npu-smi 排除

原先这里写"`npu-smi` 读 AICore 89.6–98.7% ⇒ 算力在忙"，**该结论作废**：
本机 `npu-smi` 的 AICore 列在**引擎空闲时也读 93%**，加载后读数在 118% 与 198%
之间来回跳，且不同调用之间列布局会变。这个计数器在这里不可用（§1.4）。

结论：**目前没有可靠证据排除算力受限**，也没有证据确认它。要判定必须用
torch profiler 之类的设备侧采集，而不是 `npu-smi`。

### 1.3 地板算出来了，但"是不是带宽受限"本轮没判定

```
每 rank 每步专家权重 = 3 矩阵 × 2304 × 5120 × 0.5 B(int4) × (384/8)局部专家 × 40 层
                     = 17.7 MB × 48 × 40 = 34.0 GB
权重仓分片实测专家占比 98%，总主干 292.2 GB ⇒ 每 rank 35.8 GB
地板 @ 1763 GB/s = 20.3 ms ；@ 1600 GB/s(规格) = 22.4 ms
实测固定成本 31.3 ms ⇒ 比地板慢 1.4–1.5×

**但这不等于"利用率 65%"**：地板算法假设"整步就是串行读一遍专家权重"，
而实测 F 对通信布局、上下文长度都不变——这个不变性既可能来自"读权重"，
也可能来自"固定的算子串行链"。**在拿到设备侧证据之前，不能把两者混为一谈。**
```

**交叉验证**：A3 上同一套账算出的地板 26.2 ms 与实测步长 24.79 ms 吻合到 1.0×
（`docs/DECODE-BANDWIDTH-BOUND-20261006.md`）。A2 的账落在 1.4–1.5×，
**比 A3 差得多**——这本身是个有用的信号（A2 要么读得更低效，要么 F 里有非读权重的成分），
但没有设备侧数据就无法区分。

### 1.4 ★ 为什么本文件不再引用任何 `npu-smi` 利用率数字

本轮先用了 `npu-smi` 的 `AICore(%)` / `HBM Bandwidth Usage Rate(%)` 做判断，
事后发现**这组读数在本机不可用**。证据：

| 现象 | 观测 |
|---|---|
| 引擎**空闲**（无请求）时 AICore | 读到 **93.1%** |
| 同一时刻换一次调用 | 同一张卡从 `96.8` 变成 `92.2`，列位置也变 |
| 纯 matmul 压满 15 s（实测 267 TFLOPS）时 AICore | 容器内读 **0.0%** |
| 纯 `copy_` 压满 HBM（实测 1264 GB/s）时 HBM bw | 读 **0.0%** |
| 有负载时 AICore | 在 **118%** 与 **198%** 之间逐秒跳变 |

**列还容易读错**：`npu-smi info` 里 NPU 行第 4 字段是 `Power(W)`（空闲 ~96 W），
Chip 行第 4 字段才是 `AICore(%)`。两者数值量级接近，极易混淆——
本轮就混淆过。

**结论**：`npu-smi` 的利用率列既不能证明"算力饱和"，也不能证明"带宽空闲"。
在做设备侧采集（torch profiler `analysis` / `msprof`，本机当前都因权限或返回码
失败）之前，**任何"资源利用率 X%""还有 Y 倍空间"的说法都不成立**。

刻度参考：`npu-smi` 的 `Power(W)` 与 `HBM-Usage(MB)` 是可信的（与 stderr 的
OOM 报错、实测分配都对得上）；`AICore(%)`/`HBM Bandwidth Usage Rate(%)` 不可信。

## 2. 还没做的杠杆（按"可回收 ÷ 成本"排序，含前置条件核对）

| # | 杠杆 | 机制 | 上限 | 前置条件 | 状态 |
|---:|---|---|---:|---|---|
| **1** | 让搬运与计算重叠（填 AI core 流水气泡） | 把 21 个/步、中位 69µs 的气泡连起来 | 理论上界 1.30–1.57×，**但前提未验证** | 需要设备侧证据证明气泡与权重读有关；端口仓 `armF` 只做了 `SyncAll 4→2`（已兑现 −3%） | **未试，且判定手段本轮失败** |
| 2 | 减少每步必读字节 | 换 MoE 通信形态：AllGather → All2All dispatch | 理论上大 | **需要改通信布局** | **本轮实测否决**：F 从 31.3 降到 30.9 ms（−1%），A 还从 5.89 掉到 5.69 |
| 3 | 跨层软件流水填 AIV 等待 | 两条链相位错开 | 1.39× 理论上界 | **实测否决**：拆批代价 ×1.7 > 收益（`DBO-GRAPH-VERDICT-NEGATIVE`） | 已排除 |
| 4 | 小算子融合（F3 norm+quant 等） | 减少 kernel 数与气泡 | 8–10%（打折后） | 需非逐位融合算子 + 精度分级门 | 已有量化清单，**未做** |
| 5 | 加大批 | 每 token 权重成本下降 | 吞吐向，非单流 | 与"单流延迟"目标冲突 | 不适用 |
| 6 | GMM 内核同步裁剪（armF） | `SyncAll 4→2`、`Reset 5→2` | −3%（已兑现一部分） | 已在交付镜像里 | 已做 |

### 2.1 为什么 #1 是唯一还有量级的单流杠杆

跨层流水（#3）被拆批代价封死；融合（#4）只有个位数百分点；
#2 需要重做 MoE 的专家调度，属于"换算法"而不是"调实现"。
**#1 的天花板算式（仅供参考，前提未验证）**：若 F 能从 31.3 ms 压到理论地板 22.4 ms，
整步（含 4.19 ms 边际成本）35.5→26.6 ms = **1.57×**；压到 26 ms 则约 **1.30×**。

**但 #1 的可行性完全没验证**：F 究竟是"搬运与计算没重叠"（可修），
还是"int4 权重读 + 算子串行链本来就这么慢"（不可修），本轮**没有证据区分**——
因为唯一能区分它的设备侧采集手段（`npu-smi` 利用率列）在本机失效（§1.4）。
两者的处置完全不同：
- 若是重叠问题 ⇒ 预取/双缓冲/调整 kernel 排布，属于实现层，有 1.3–1.6× 空间；
- 若是 int4 权重的读带宽天然打折 ⇒ 地板就是 31 ms，**单流已经到顶**，只剩融合那 8–10%。

**下一步必须先做的判别实验**：单独跑一次 `npu_grouped_matmul` 的微基准
（int4 权重、48 专家、decode 形状），看它单独能达到多少 GB/s。
若微基准本身就是 ~1140 GB/s ⇒ #1 不存在，单流已到顶；
若微基准能到 1700 GB/s ⇒ #1 成立，去查整步为什么比地板慢 1.4–1.5×。

> **本轮的尝试与结果（诚实记录）**：试了三种参数组合（`group_list` 用 counts /
> cumsum、加 bias），`npu_grouped_matmul` 全部返回 `aclnnGroupedMatmul failed,
> error code 161002`。说明手工构造这条调用缺了一环（scale 的 per-channel 组数、
> 或 per-token 量化的额外约束），**判别实验本轮没做成**。
> 不要照抄这里的参数直接用于生产——真正的调用形状见
> `vllm_ascend/quantization/methods/w4a8/w4a8.py:464`（`apply_gmm1_act_quant`），
> 那里 `scale` 需要 `unsqueeze(-2)` 成 `[E,1,N]`、并且走的是引擎已经量化好的
> `pertoken_scale`。要做这个判别，最省事的做法是**在引擎里打日志**量出
> GMM1/GMM2 的实际耗时与读取字节，而不是在外面重新构造调用。

### 2.2 ★ "必读全部 48 个本地专家"是 AllGather 的数学后果，不是实现缺陷

起服日志：`FlashComm1 is disabled. Using flashinfer_all2allv`，同时 `V41_MOE_COMM_ALLGATHER=1`。
实测分两步算：

**AllGather（当前）**：每个 rank 拿到**全部** token 的 hidden states，但只用自己的 48 个专家算。

```
每步 token 总数 = 8 rank × 6 token(batch=1, A=5.82) = 48
每步路由决策   = 48 × top-6 = 288
摊到本 rank 48 个专家 = 6.0 token/专家  ⇒ 48 个专家**全部命中**
⇒ 必须把 48 个专家的权重全部读一遍 = 34–35.8 GB/步
```

**All2All dispatch**：每个 rank 只收发给自己的 token。

```
每 rank 每步专家命中 = 288 / 8 = 36 次，distinct 专家数远小于 48
⇒ 只读约 5.7 GB/步（按 8 个 distinct 估）⇒ 地板从 19.3 ms 降到 3.2 ms
```

（原先这里用"AICore 94% 却带宽只 65%"解释此事，该组读数已作废，见 §1.4。）
但换 All2All 的代价是**每步多两次集合通信**（dispatch + combine），
在单流 35 ms 的步长下未必划算——这正是需要实测的部分，**不能只凭算术结论拍板**。

> ⚠️ **2026-10-20 实测（两轮，第二轮才是真的）：这个方向实测无收益。**
>
> **第一轮是空实验**：只设 `V41_MOE_COMM_ALLGATHER=0`，引擎仍走 FUSED_MC2——
> `ascend_forward_context.py:317` 的 `enable_fused_mc2 == 1 and world_size <= 32`
> 无条件短路排在 AllGather 分支之后、AllToAll 之前。那次的 163.3→165.6 两边同路径。
>
> **第二轮（真做）**：同时 `enable_fused_mc2=0`（并去掉 additional-config 里的
> `enable_fused_mc2`），确认走的是 AllToAll：
>
> | 配置 | ctx | step(n=1) | c/请求 | **F** |
> |---|---:|---:|---:|---:|
> | AllGather / fused_mc2=1（默认） | 8K | 35.52 ms | 4.19 | **31.33 ms** |
> | fused_mc2=0（AllToAll 生效） | 8K | 34.26 ms | 3.35 | **30.91 ms** |
>
> **F 几乎不变（31.3 → 30.9）** ⇒ 换通信形态**没有降低每步必读字节**。
> 结合 F 对上下文长度也不敏感（8K 与 32K 都是 31–32 ms），
> **"减少必读字节"这条路在本配置下走不通**，无论走 AllGather 还是 AllToAll。
> 顺带：AllToAll 下 A 从 5.89 掉到 5.69（更多路由抖动），精度侧也没有收益。
>
> **教训**：A/B 前先确认开关真的改变了代码路径；否则"没变慢"会被误读成"这个方向没收益"，
> 而实际上是你根本没改动任何东西。

## 3. 与既有结论的关系（重要：不要重复走）

- `docs/DECODE-BANDWIDTH-BOUND-20261006.md`（A3）已判定 decode 带宽受限，
  并列出同样三条杠杆。**本文件是在 A2 + 1017 权重上重新定价，不是新发现。**
- `docs/STEPTIME-DECOMP-AND-CROSSLAYER-PIPELINE-20261007.md` 的跨层流水方案
  **在 A2 上账更不利**：A3 的固定成本占比低于 A2（A2 是 88%），
  拆批会让边际成本（A2 为 4.19 ms/请求）翻倍。
- `docs/FUSION-CANDIDATES-20261007.md` 的 8 族清单仍然是 #4 的输入，
  但它给出的 19.1% 是**聚合暴露**，不是可回收量。

## 4. 复现方法（都不需要解析 prof 二进制）

```bash
# 1) 并发扫描 -> 固定成本 / 边际成本
for n in 1 2 4; do python3 concurrency_probe.py http://127.0.0.1:<PORT> longgen-prompt.json $n 256; done

# 2) HBM 带宽微基准
python3 hbm_bw.py        # torch.sum / copy_，0.05–0.2 GiB，200 次平均

# 3) AICore 稳态占用（起服后、有负载时）
npu-smi info | grep -E "^\| [0-9]+ +910"

# 4) 专家字节数（两种独立算法互校）
#    a) 结构式：3 * moe_intermediate * hidden * 0.5B * (n_routed/EP) * n_layers
#    b) 分片式：safetensors 抽样求 experts 键占比 × 主干总字节 / EP
```
